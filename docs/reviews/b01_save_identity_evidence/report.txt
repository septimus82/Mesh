WHAT CHANGED (engine/save_runtime/{entity_state,schema,io,payloads,normalize,ux_codes}.py, engine/save_manager.py,
engine/scene_lifecycle_controller.py; digest.py untouched)
- SAVE_SCHEMA_VERSION 2 -> 3. Records: keying "id" (mesh_id + occurrence) or "name" (id-less); total sort key; container adds
  scene_path, counters, unresolved. v2 -> v3 runs in memory only (tags records keying:name, legacy:true).
- Binding: id records by id; duplicates of one id bind by order + place only when record and sprite counts agree; id-less
  records bind to id-less sprites by name, then by unique place; v2 records by name, then by unique place cross-checked
  with the save's own snapshot. Nothing is "last wins"; nothing is applied on a guess.
- Records whose entity is absent at load (entity_missing) are unmatched too (owner rule, master review): reported as
  entity_missing with the same counts, and kept as unresolved (reason entity_missing).
- Unbound records -> diagnostics (entity_id_ambiguous / entity_legacy_ambiguous / entity_nameclash, roll-ups
  entities_unbound / entities_unresolved), stderr, the load attempt's diagnostics, and a player toast; kept as
  saved_entities.unresolved in every later save (dedup by scene_path + SHA-256), retried each load against sprites that
  received no record, removed only by binding or manual edit.
- Recovery: load never rewrites a v2 slot; first v3 save over a pre-v3 slot writes <slot>.json.v2.bak and verifies it
  (SHA-256 of a fresh read) or refuses (slot byte-identical, save.write.v2_backup_failed, toast); an existing backup is
  never replaced (<slot>.json.v2.<sha8>.bak); a v4 save is refused by the existing newer-version error.
- A v3 save's records name their room; the first apply onto the room being left skips another room's records.

POINTS FOR THE REVIEWER (facts, not decisions)
1. Strict mode. The design says entity_id_ambiguous is ERROR ("WARN non-strict; fails in strict"). The production slot load
   runs with SLOT_POLICY.strict_restore=True, where any ERROR refuses the load (LOAD_APPLY_FAILED): that would refuse
   exactly the saves T16/T33 require to load. Implemented: the three binding codes are ERROR when apply_entities_ex is
   strict (a developer's strict check, T16 asserts it) and WARN in the slot load (strict_binding=False). Loads are never
   refused for an unprovable identity.
2. Records whose entity is absent are carried as unresolved (reason entity_missing), retried under the same provable rules
   (id records by exact id; name records by unique place; never by name alone). Consequence: expired projectiles
   accumulate in saved_entities.unresolved (deduplicated by content) until bound or edited out; that is the owner's rule.
3. The first apply (onto the room being left) reports nothing to stderr and its identity diagnostics are replaced in the
   load attempt by the second (saved room) apply's, so a clone case is not reported twice.
4. A retried (carried) name-keyed record binds only by unique place, never by name alone (a stale record must not land on
   a newcomer that merely shares a name).
5. A sprite with neither name nor id is still not serialised (as on the base).
6. A slot that is not parseable as a save is also backed up before being overwritten (its version cannot be read).
7. Unresolved records live with the game session (the GameState object): a New Game drops them; a load replaces them.
8. Wrong-room guard: same room = equal room_key or equal absolute path.
9. The backup name is <slot file>.v2.bak (e.g. slot1.json.v2.bak), like the diagnostics sidecars.
