# Packaging: what a pip-installed Mesh carries

A wheel only contains files inside its Python packages (`engine`, `mesh_cli`). `MANIFEST.in` lists the source
distribution's data, but none of it reached the wheel, so a pip-installed Mesh created projects with no starter files
and no default input bindings. This change bundles exactly the engine's own files that a pip install needs, and
nothing else.

## What an installed engine reads from itself (inventory, measured)

Since `643970a` (2026-06-30), a game's content resolves only inside its project. The engine reads from its own
install in just two places:

| Reader | What it reads | Why |
|---|---|---|
| `project_scaffold.create_project` | `config.json` | A new project's default `input_bindings` |
| `project_scaffold.create_project` | The monster starter files and the battle audio | Copied into every new project |
| `paths.resolve_engine_bundled_path` | `assets/data/monster_*` | The bundled monster data (the only engine fallback content isolation keeps) |

**How it was measured:** the same project was created from the source tree and from a wheel installed in a clean
venv, outside any repository, for each template, and the results compared. The installed copy was missing these files
and logged "Engine starter asset missing" for each:

| Group | Files |
|---|---|
| Monster data | `assets/data/monster_species.json`, `monster_moves.json`, `monster_type_chart.json` |
| Battle sounds | `assets/sounds/attack.wav`, `die.wav`, `hit.wav`, `ui_click.wav`, `ui_close.wav`, `ui_hover.wav`, `ui_open.wav` |
| Battle music | `assets/music/dungeon_theme.wav` |
| Starter sprites | `assets/sprites/animated_player.png`, `shelltide.png`, `sproutling.png` |
| Engine config | `config.json` |

**`packs/` is not needed.** Templates generate a new project's scenes and world, and content isolation means a game
never reads the engine's own packs. The original wheel test (2026-01) expected the engine's pack presets to load
without a project. That predates content isolation, so it was replaced (see Tests).

## Licences and redistribution

| Files | Origin | Bundled? |
|---|---|---|
| The 8 WAVs | Generated by Mesh's own `tooling/generate_sounds.py` and `tooling/generate_music.py` (synthesised tones, slides and noise, no samples) | **Yes:** Mesh's own work |
| The 3 monster JSONs | Written for Mesh (MON-0b, 2026-06-29) | **Yes:** Mesh's own work |
| `config.json` | Mesh's engine configuration: settings only, no local paths or personal data (checked) | **Yes** |
| `sproutling.png`, `shelltide.png` | Committed 2026-06-30 as "the user sprite sheet". The owner's art; its source and terms aren't recorded | **No: not confirmed** |
| `animated_player.png` | Initial import, origin not recorded | **No: not confirmed** |

**Blocker for the three sprites.** Redistribution permission isn't confirmed, so they are not bundled.

- **Effect:** a project created from a pip install lacks them. The scaffold logs that they aren't bundled and
  carries on, and monster battles fall back to the built-in placeholder for a missing sprite sheet (PR #311).
- **Fix, either of:**
  - **The owner confirms** they may be redistributed (for example: drawn by the owner, or a tool whose terms let
    the owner distribute its output). Add them to the allow-list.
  - **Replace them** with sprites Mesh generates itself, as `tooling/make_starter_art.py` does for the starter
    characters on the redesign branch.

## Method

- **The allow-list.** `pyproject.toml`'s `[tool.setuptools.data-files]` lists the 12 files by name, so nothing goes in
  by accident. pip installs them under `<prefix>/share/mesh-engine/` (`<venv>/share/mesh-engine` in a venv), the
  conventional place for an application's shared data. Putting a bare `config.json` and `assets/` at the top of
  `site-packages` would collide with other packages.
- **The lookup.** `engine.repo_root.bundled_data_roots()` / `bundled_file()` is the one place that finds them:
  - the source tree first (a checkout or an editable install: unchanged for development);
  - then `share/mesh-engine` under the install prefix, including `pip install --user`.
- **Who uses it:** `project_scaffold` and `paths._engine_install_roots` use the lookup instead of the two locations
  they each had (`sys.prefix` and the folder above `engine/`).

**To bundle another file:** check its licence, add it to `[tool.setuptools.data-files]`, and the wheel test will
expect it.

## Tests

- **`tests/test_wheel_bundles_engine_data.py`** (slow; it builds a wheel). Replaces `test_wheel_includes_pack_data.py`.
  - The wheel bundles exactly the allow-list, and no `packs/`.
  - It is installed into a clean venv (`--no-deps`, plus the declared `jsonschema` and `pillow`; no graphics stack).
  - From an empty folder outside any repository, with `MESH_REPO_ROOT` and `PYTHONPATH` cleared:
    - a new project gets the bundled starter files and the default input bindings;
    - the only missing-file warnings are for the three unconfirmed sprites;
    - the bundled monster data resolves from `share/mesh-engine`.
- **`tests/test_bundled_data_roots.py`** (fast): the source tree comes first, and an install's `share/mesh-engine` is
  found.
